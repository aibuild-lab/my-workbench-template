# Update your workbench and programs

Use the existing workbench. Program updates come from each approved remote's `student` branch. Commit messages are release notes. Enrollment and package-to-Git adoption use `aibl-enroll` first.

## Steps

1. **Check location and work.** Follow `aibl-enroll` step 1 to verify the workbench and private origin. `git status --porcelain --untracked-files=all` must be empty. Otherwise stop for `aibl-checkpoint`; never stash, discard, or reset. Record the starting commit for recovery.
2. **Refresh core skills only after choices.** Use the exact `template` remote `https://github.com/aibuild-lab/my-workbench-template.git` (equivalent GitHub SSH URL is allowed); stop on an existing different URL. Fetch `main`, and pin the fetched commit for this preview. List the four supplied core folders (`aibl-personalize`, `aibl-checkpoint`, `aibl-enroll`, `aibl-update`) under both `.claude/skills/` and `.agents/skills/`, and `.claude/hooks/update-check.mjs`. For each differing path show `git diff HEAD template/main -- <path>` and ask keep mine or take template. Treat committed differences as possible customization, not permission to replace. Reject symlinked destinations and existing ignored/untracked collisions. Only after approval use `git checkout template/main -- <path>`. Skip kept paths. Stage and commit only the approved paths; never bulk-checkout the template. Do not fetch a different revision between preview and apply.
3. **Preserve settings.** If `.claude/settings.json` is absent, offer the template's setting as a separate approved addition after checking for ignored/symlink collisions. If present, leave it unchanged. Explain that the copied hook is not active unless the existing configuration invokes it. The student may approve adding only the missing SessionStart hook entry after seeing the JSON diff; preserve every existing key and hook and avoid duplicates. Invalid JSON stops the settings change. Otherwise the explicit check works without changing settings. This Claude hook does not establish a Codex session-start hook.
4. **Check connected programs.** Run `node .claude/hooks/update-check.mjs --json`. If Node or the hook is unavailable, manually check only the known program remotes in `aibl-enroll`, verifying URL and fetching `student` before counting commits. Unknown remotes are not programs. A failed or empty check is unknown, never up to date. A remote with no common history is not yet enrolled: use `aibl-enroll`. No connected programs means offer enrollment. Zero pending commits means no program update; report any core changes separately.
5. **Explain the program changes.** For each connected program with a newer edition, read `git log --format='%s' HEAD..<remote>/student` and `git diff --stat HEAD...<remote>/student`. Apply the enrollment tree and collision checks to the incoming branch and its changed/deleted paths. Reject any change to personal folders, root instructions/settings, or template-owned core skills. (A program never ships root instructions. The one narrow exception is step 7's previewed refresh of the "your team" block in the root `AGENTS.md`, offered only when this update changed `workforce/HOUSE.md`, as its own commit on a separate yes.) Compare `workforce/VERSIONS.json` when supplied, otherwise the `components` in `.aibl/programs/agent-workforce.json`. Match components by ID; show additions, removals and changed versions/fingerprints. Missing or pending versions remain unknown; show exact Git revisions instead of inventing numbers. Never edit publisher version records or treat their presence as approval. Compare student edits since the common ancestor against incoming changes, including deleted supplied files. Explain likely conflicts without promising Git will conflict on every overlapping edit. Recommend incoming fixes for unchanged supplied files and explicit choices for personalized files.
6. **Approve and merge.** Save the pre-update commit and exact fetched commit, show the preview, and obtain a yes. Recheck the worktree and ref. Run `git merge --no-ff --no-commit <remote>/student`. For conflicts offer keep mine, take the program's, or combine specifically approved changes, explaining each cost. Resolve only chosen paths, then stage them. For Chief's name, show the old personalized display-name line and propose preserving it in the updated Claude or Codex definition without changing agent IDs, syntax, or role instructions. Never infer a name from a filename or rewrite other edits. Show the staged diff before committing. If canceled before commit, `git merge --abort`; after commit offer a separately approved Git revert of this update, never a reset of student history.
6.5. **Make the update live.** The merge put the right files on disk; the apps do not know it yet. First rebuild the registry so the roster matches what arrived:
   ```
   python3 workforce/shed/generate-registry.py --root . --date <today, YYYY-MM-DD>
   ```
   On Windows, if `python3` is not found, use `python`, then `py -3`.
   If `git status --short` shows `workforce/shed/registry.yaml` changed, include it in the checkpoint at the end of this step. If the script is absent, say so and carry on; do not hand-edit the registry.
   Then prove one agent answers. Start a new session in this same folder, ask the program's entry agent a question through the app's supported route, and read its actual reply back to the student. A file that parses is not proof; a reply is. If nothing answers, say so and stop rather than reporting the update as done.
   **Keep Claude Code's agent menu and the bridge skills in step (Claude Code only; Codex has no such menu).** The desktop app's `@` menu lists agents only from the student's own user folder (`~/.claude/agents/` on a Mac, `.claude\agents` in the user folder on Windows), never from this workbench, and the course teaches picking agents there (Learn card 0.3 step 6, Lesson 6). With the same name in both places the menu shows the user-folder entry but this workbench's file is what runs. The user-folder copy runs only when it has no match here (a retired or renamed seat) or when the student picks it with another folder open, so keep the entries identical and remove leftovers. The bridge is the same: a thread opened outside this workbench only has the `aibl-bridge` and `aibl-bridge-setup` skills if real copies sit in `~/.claude/skills/`. Run `node .claude/hooks/update-check.mjs --agent-menu` yourself and explain what it found to the student in plain words with the full folder paths; do not hand them the command. Its lists, for agents and (under `skills`) for the bridge skills: `missing` (not there yet), `changed` (a course-made copy that differs from this workbench's: a version the course published, or one a workbench placed), `leftover` (a retired course agent this workbench put there), and `edited` (a copy whose bytes match nothing the course or a workbench made, so it carries the student's own edits). Ask once for the first three; only on their explicit yes run `node .claude/hooks/update-check.mjs --agent-menu-apply` yourself. Make the offer even when nothing is missing or changed: the apply also records that this workbench uses the copies already there. Ask about each `edited` copy separately, in these words: "Your copy of NAME has your own edits; replace it with the course version? The old one goes to a backup." Only on that yes add `--replace-edited NAME` to the apply; otherwise leave it exactly as it is. The apply touches only the course's own items: the `aibl-` agents on the allowlist inside that file (every agent the course has ever shipped) and the two bridge skills. It makes real copies (never through an existing link, scripts kept runnable), records in `~/.claude/aibl-agent-menu-placed.json` which workbench placed or uses each copy, and moves leftovers and replaced copies (a link moves as a link) to a uniquely named, dated `~/.claude/aibl-agent-menu-removed/` folder instead of deleting them. A leftover is only a course agent that the program's verified `student` branch once shipped, that its current edition no longer ships, that this workbench no longer has, and that this workbench itself placed in the menu, unchanged since, with no other known workbench still holding that name. Everything else is left alone: `not_ours` (the student's own agents, `aibl-` named or not, a terminal Chief rendered on this computer, a copy another workbench placed), `other_workbench` (a copy that matches another known workbench's, which this workbench does not replace), `case_conflict` (a file whose name differs only in capital letters, which Mac and Windows treat as the same name; it is never touched, so tell the student and leave it), `skipped` (an `aibl-` agent the student made in this workbench, which is never copied), the student's own skills, and anything of Codex's. If the apply answers `busy`, another update is running: wait a minute and run it again. If the report's status is `linked_folder`, the student's Claude agents or skills folder is a shortcut to another folder: do not offer the fix (it refuses anyway), tell the student in plain words that nothing was changed and that the course team can help make it a real folder. Show its report, then tell the student to quit the app fully and open it again (the menu reads that folder only at launch) and to start a new thread before typing `@`. If they decline, the lessons' start requests still work because they name the agent. Never write outside the workbench unasked.
7. **Verify what arrived.** Inspect the actual diff against the saved pre-update commit and verify personal files, settings, and Chief's approved name. Report exact revisions, changed components, and any kept customizations; version metadata alone cannot describe a customized file. Preserve historical package receipts, and never run package repair/update on Git-managed course files. Then, one at a time and each only on the student's yes (run every command yourself; never hand the student one):
   - **"Tell my assistant about my team", again,** only when `git diff --name-only <pre-update commit> HEAD -- workforce/HOUSE.md` shows this update changed it. Re-render, preview, and commit exactly as `aibl-enroll` step 7 describes: only the `house:begin` ... `house:end` block in the root `AGENTS.md` may change, and `CLAUDE.md` may change only by adding a missing `@AGENTS.md` line or removing an older render's `@workforce/HOUSE.md` line; normally it does not change at all, because it already reads `@AGENTS.md`, as one commit, "Tell my assistant about my team". Any other change stops.
   - **Refresh the real copies** of the course's agents and bridge skills: step 6.5's offer, if the student has not already answered it in this update.
   - **Record my home workbench,** only when `node .claude/hooks/update-check.mjs --home-workbench` reports `not_recorded`, `unreadable` or `pointer_is_a_link`: the same offer as `aibl-enroll` step 7. If it reports `another_folder`, just tell the student which folder is recorded and offer to switch; do not switch unasked.

   Offer a checkpoint to the student's private origin only. Start a new session in the same folder and verify an actual named-agent response through the installed supported route. Do not switch clients or call file presence runtime success.

## Rules

- Program merges use only verified `<remote>/student`; `template/main` is used only for the approved core-file refresh.
- Never merge over a dirty tree, overwrite ignored files, resolve a surprise conflict, or apply a changed preview without a new decision.
- Never push except through the student's separately requested checkpoint to their private `origin`.
- Nothing here installs software, grants access, changes global settings, or sends work. The only writes outside the workbench are the real copies of the course's own agents and bridge skills in the user's `.claude` folder, with their record, lock and backup folder (step 6.5), and the one file `~/.aibl/workbench.json` (step 7), each written only on the student's yes. The student's own agents and skills, in Claude Code or Codex, are never moved, replaced or deleted.
