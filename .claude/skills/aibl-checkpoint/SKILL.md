# Checkpoint

A checkpoint is a named snapshot of chosen files, kept in two places: this computer and the private copy on GitHub. Saving a file is not a checkpoint. A checkpoint is the thing you can go back to.

## In Codex: one permission for each protected write

In Codex, an agent can't change this folder's history (`.git`), anything outside this folder, or use the network, unless the owner allows that step. Claude Code has no such step: there, run the steps as written. In Codex, every write in the table below follows these five rules, and each part that makes one says so with "(Codex: one permission per write.)":

- **One plain line first.** Before the command, say in one plain line what is about to change, then the course's Week 1 words for the box: "If Codex asks you to allow a save to your workbench's history, that's this save; choose to allow it." for a save, and "If Codex asks you to allow it, that's this step; choose to allow it." for any other write. Use the part's line from the table, with the label and the files in plain words. Never show the command, a file path or a word in capitals in that line.
- **Its own command, with the permission asked together with it.** Run each write as one command on its own, never joined to another with `&&`, `;` or `|`, and never inside a script you write to run several. Request the app's permission together with that exact command when you run it: ask to run it outside the sandbox, with a one-line reason that names the same step as your plain line, so the box the owner sees names the step you just named. Never try it first and ask only after it fails: Codex does not offer the permission on its own. If a write you ran without asking fails with a read-only or permission message (such as "Unable to create .git/index.lock: Permission denied"), that is not the owner's no: run the same command once more, alone, with the permission asked.
- **One line and one box per write.** When every file in the save is already tracked, save with one command, `git commit -m "<label>" -- <files>`, so there is one box, not two; a new file needs `git add -- <file>` first, its own command. Read-only commands (`git status`, `git diff`, `git ls-files`, `git log`, `git show`) need no line and no permission.
- **Never a terminal step for the owner.** You run every command. Never hand the owner a command, a box with a command in it, or a step in a terminal or PowerShell, even when a permission is refused.
- **If it isn't allowed, wait.** If the owner doesn't allow it, or no box comes (for example the session's approval policy is never, so no permission can be asked), stop at that step. When you stop there, that reply is exactly two lines: the step's plain line, then its waiting line, word for word from the table, even when you knew before running it that no box could come. Nothing before them and nothing after: no note that a permission is needed or can't be asked, no quote of this skill, no file link, no word about the app's settings or policies. Then do nothing else: no other command, no other way to make the same change, no choices of your own, and never say or suggest the step happened ("Saved in two places" only after both the save and the push worked). On "try again", recheck that the files are as they were, say the plain line again, and run the same command with the permission asked.

The waiting lines are true because each command changes nothing when it is refused: a refused commit leaves the files as they were, and a refused push leaves the save on this computer, so "try again" runs only the push.

## Save

1. Look. Run `git status --short` and `git diff`. Tell them what changed in plain words, one line per file. Name files, not hashes. Example: "Your note in context/project.md got three new lines. Nothing else changed."
2. Leave out anything private: `.env` files, anything under `.aibl-local/`, `runs/`, `quarantine/`, `logs/` or `library/originals/`, log files, the voice samples and voice package (`work/course/staff/voice*`), account records (`*-accounts.yaml`), the agents' local notes (`.claude/agent-memory-local/`), settings files, and client material they did not ask to include. Before staging or pushing, run `git ls-files -- runs/ quarantine/ logs/ "*.log" library/originals/ "work/course/staff/voice*" "*-accounts.yaml" .claude/agent-memory-local/ .aibl-local/ .env ".env.*" .claude/settings.local.json`. Example key files (`.env.example`, `.env.sample`, `.env.template`) may show up in that list and are fine to keep. If it lists any other path, stop the checkpoint: these local-only records are already tracked, and ignore rules do not remove them from Git. Name the paths without printing their contents. Say in plain words: "These files were saved in earlier snapshots. If you say yes, they stay on this computer and stop going into new snapshots; the earlier snapshots keep them. If this workbench is also on a second computer, its copies go away the next time it pulls, so copy them first. I recommend yes. Stop including them?" On a yes, if `workforce/skills/aibl-checkpoint/SKILL.md` exists, follow its untrack step; otherwise run `git rm --cached -- <path>` once per listed file (never `-f` or a folder name), then carry on with the save. On a no, the checkpoint stays stopped and nothing changes. Ask the owner to review how to stop tracking them while retaining the local files; do not delete files, untrack them or rewrite remote history on their behalf. An earlier remote copy remains even after untracking. If the command lists nothing, or only example key files, continue. Never force-add these local-only paths. Say what you left out and why. The course's notes under `work/course/staff/` (the bookmarks `continuation-*.json` and `agent-menu.json`, `progress.md`, the founder brief) are the owner's own records and are saved like any other file; only `voice*` and `*-accounts.yaml` there stay out. Never tell the owner the course keeps a bookmark on this computer only. (Codex: one permission per write. Each `git rm --cached` is its own command after its own plain line.)
2.5. **The course's privacy check.** First look whether this is an Agent Workforce workbench: it is when either of the course's enrollment stamps exists in this folder, `.aibl/programs/agent-workforce.json` or `.aibl/workforce-student-edition.json`, or when `workforce/runtime/privacy_check.py` exists. Only look at whether these files exist; don't open them. When none of the three exists (Camp, Essentials, Team HQ, or no program), skip this step and the check in step 4. When a stamp exists but `workforce/runtime/privacy_check.py` does not, refuse: make no save, stage nothing, and say in plain words: "I didn't save. This workbench has Agent Workforce, but the course's privacy check (workforce/runtime/privacy_check.py) is missing, so I can't make sure your customer mail and job records stay out of the save. To bring it back, run the update paste on Agent Workforce card 0.3, Get your organization, in Learn. Then ask me to save again. If you see this again after the update, post in the course channel and the course team will help you bring it back." Give no Git commands for bringing the file back. A missing check never counts as a pass: don't fall back to step 2's list alone, and never write, copy, download or restore the check yourself. Nothing is deleted or moved. When the check file exists, before staging anything, run `python3 workforce/runtime/privacy_check.py gate` from the workbench folder. On Windows run `py -3` in place of `python3` here and in step 4, or `python` if `py` is missing (`python3` on Windows is usually a Store stub that runs nothing). It reads only and changes nothing. Only exit 0 with a printed line that starts `Clear:` is a pass; then carry on. Anything else stops the save before anything is staged:
   - Exit 3 means it found something: a private file Git already tracks, a line missing from `.gitignore`, or a `.gitignore` line that could undo the protection. Tell them in plain words what it found: name each file or line and the kind of record it named (customer mail, job records, voice material, account records, keys), without opening or printing the files. Then say what they can do, using the check's own fixes and only on their yes: for tracked files, the same choice as step 2 ("they stay on this computer and stop going into new snapshots; the earlier snapshots and the GitHub copy keep them"), done with `python3 workforce/runtime/privacy_check.py untrack --yes "<their yes, word for word>"`; for missing lines, `python3 workforce/runtime/privacy_check.py ignore --yes "<their yes, word for word>"`, which only adds lines to the end of `.gitignore`. A line that could undo the protection, or an odd character in a `.gitignore`: show them the file and the line number, and tell them how to fix it themselves: open that `.gitignore` in their editor, delete that one line (or the odd character), save the file, then say "save" again; or ask their course companion for help. Never edit or remove that line yourself and never offer to, even if they ask you to. The save stays stopped until they have fixed it and the gate passes. After a fix, run the gate again; only its pass continues the save. On a no, the save stays stopped and nothing changes.
   - Exit 2, no Python, no readable output, or any other answer means the check could not run. Make no save. Say in plain words that the privacy check could not run, so nothing was saved, and that Gigawatt or their course helper can repair it. A check that could not run never counts as a pass.
   - Never delete, move or edit their files, never force-add, and on Windows never build a shell command from a file name. The check reads file names and folders, not what is inside them, and it cannot reach copies already in earlier snapshots or on GitHub; say so when it matters, and don't promise more than that. Inside Codex's sandbox the gate and the staged check can run, but an untrack, staging and the commit run outside it, on their yes. (Codex: one permission per write. The untrack is its own command after its own plain line; `ignore` writes only `.gitignore`, inside this folder, and needs none.)
3. Propose a label in their words, under ten words. Example: "Interview answers, first pass." Let them change it.
4. Stage the named files only (never `git add -A` or `git add .`). If step 2.5 ran, run `python3 workforce/runtime/privacy_check.py staged` now, before the commit (`py -3` on Windows). Exit 0 continues. Exit 3 means a private file got staged even though no ignore rule caught it (for example through a folder link or a short Windows name): make no commit, run `python3 workforce/runtime/privacy_check.py staged --unstage`, which takes only those files out of the snapshot and leaves them on this computer (it exits 3 even when it worked, so read what it prints), tell them in plain words which files were held back and why, and stop. If it could not run, make no commit, say the privacy check could not run so nothing was saved, and stop. Then commit with the label, then push to `origin` on the current branch. Then say: "Saved in two places: on this computer, and at github.com/<user>/my-workbench." (Codex: one permission per write. The commit and the push are two writes, each its own command after its own plain line; a new file's `git add` is one more, and so is `staged --unstage` when the staged check found something.)
5. If the push is refused because the copy on GitHub has moved: stop, explain in one sentence, pull, then push again. Never force-push. (Codex: one permission per write. The pull and the second push are each their own command.)

If Git asks who they are (no local name or email), set `user.name` and `user.email` for this folder only, using their GitHub login and its noreply address. Never change global settings. (Codex: one permission per write. Each `git config` is its own command.)

Never tell the student a skill or a procedure requires something, and don't quote this file or name its steps. Say in plain words what they're choosing and why it's safe.

## Bring a file back

When they say a file is gone or wrong:

1. Run `git log --oneline -- <file>` to find the snapshots that have it. Show the labels. Let them pick.
2. Show the old version first (`git show <commit>:<file>`), so they see what is coming back before it moves.
3. Restore only that file: `git checkout <commit> -- <file>`. Nothing else moves. (Codex: one permission per write.)
4. Say what came back and from which label. Then offer a new checkpoint, so the restore is itself saved.

Never run `git reset --hard`. Never rewrite history that has been pushed.

## What to say when it is done

The label, the files in it, and the two places it now lives. One line each.
