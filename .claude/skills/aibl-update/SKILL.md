# Update your workbench and programs

Use the existing workbench. Program updates come from each approved remote's `student` branch. Commit messages are release notes. Enrollment and package-to-Git adoption use `aibl-enroll` first.

## In Codex: one permission for each protected write

In Codex, an agent can't change this workbench's history (`.git`), its `.agents` or `.codex` folders, or anything outside the workbench, and can't use the network, unless the student allows that step. Claude Code has no such step: there, run the steps as written. In Codex, every write in the table below follows these five rules, and each step that makes one says so with "(Codex: one permission per write.)":

- **One plain line first.** Before the command, say in one plain line what is about to change, then "Codex may ask you to allow it. If it does, choose Allow." (for a step that only uses the network: "Codex may ask to use the network. If it does, choose Allow."). Use the step's line from the table, with the update's own words for what it brings (for a new week, its name, such as "Week 2"). Never show the command, a file path or a word in capitals in that line.
- **Its own command, with the permission asked together with it.** Run each write as one command on its own, never joined to another with `&&`, `;` or `|`, and never inside a script you write to run several. Request the app's permission together with that exact command when you run it: ask to run it outside the sandbox, with a one-line reason that names the same step as your plain line, so the box the student sees names the step you just named. Never try it first and ask only after it fails: Codex does not offer the permission on its own. If a write you ran without asking fails with a read-only or permission message (such as "Unable to create .git/index.lock: Permission denied"), that is not the student's no: run the same command once more, alone, with the permission asked.
- **One line and one box per write.** Two writes in a row get two plain lines and two boxes. Read-only commands (`git status`, `git rev-parse`, `git rev-list`, `git ls-tree`, `git ls-files`, `git merge-base`, `git cat-file`, and the reports that say they write nothing) need no line and no permission.
- **Never a terminal step for the student.** You run every command. Never hand the student a command, a box with a command in it, or a step in a terminal or PowerShell, even when a permission is refused.
- **If it isn't allowed, wait.** If the student doesn't allow it, or no box comes (for example the session's approval policy is never, so no permission can be asked), stop at that step. Say the step's waiting line from the table: what isn't in or isn't saved, that nothing else changed or nothing is lost, and how to retry. When you stop there, that reply is exactly two lines: the step's plain line, then its waiting line, word for word from the table, even when you knew before running it that no box could come. Nothing before them and nothing after: no note that a permission is needed or can't be asked, no quote of this skill, no file link, no word about the app's settings or policies. Then do nothing else in this update: no other command, no other way to make the same change (another command, a script, editing files inside `.git`), no choices of your own, and never say or suggest the step happened. On "try again", recheck that the workbench and the pinned commits are as they were, say the plain line again, and run the same command with the permission asked. If anything changed meanwhile, preview again and ask again.

## One combined question

Steps 2, 2.5 and 3 ask once, together, before any of them writes: template versions the student hasn't changed (a copy that matches a version the template shipped, or a copy the workbench doesn't have), the privacy lines, and the update check. In these words, leaving out any line that doesn't apply; if nothing applies, there is no question:

```text
These updates are ready. None of them changes how your team works:

- Newer versions of your workbench's skills and its update check. You haven't changed them, so they're safe to take.
- A few lines that keep private records, like job folders and customer mail, out of what you save to GitHub.
- A check that tells you when an update is out each time you open your workbench. Codex asks you to trust it once.

Take all the recommended updates? I can show you the details first. If you say no, everything stays as it is.
```

A plain yes, such as "take it", answers the whole list: don't ask again about any item on it. If they ask for the details, show what they ask for: the diff, the exact lines, or the exact hook as JSON, then ask again. They can say yes to some and no to the rest. A no to any item keeps that item as it is. A copy that differs from every version the template shipped, or one you can't tell about, gets its own question, in its own message after the student has answered this one, and a yes here never covers it. If the student already answered this question in the update prompt, use that answer and don't ask again. A yes applies each step exactly as it is written below, with its own commit. The course update's preview in step 6, the team settings and the team note keep their own yes, because those change how things behave. Yes or no here, go on to them.

## How the other questions read

Keep each to a few plain lines, in these words or close to them. Offer the details; show them only if asked.

- **The course update:** what it brings in two or three plain lines (for example new lessons, updated agents), "Your own work isn't touched. I recommend yes. Bring it in?"
- **Team settings:** "This adds your team's rules, so your agents ask you before anything is sent. It's for Claude Code, so it does nothing if you only use Codex, and it's safe to say yes either way. I recommend yes. Add them?" Ask this in Codex too: you can't tell whether they also use Claude Code, and without it Claude Code has no ask-before-sending rules.
- **The team note:** the line in step 7, then "I recommend yes." After their yes, say what the note tells their assistant in one or two plain lines and offer to show it, then ask "Add it?"
- **The home workbench record:** "This writes one small file outside the workbench that records this folder as your team's home, where its registry, charter and receipts stay. Start your agents in this folder. I recommend yes. Record it?"

## Rules

- **Every question says in plain words what it does and which answer you recommend.** Don't show a raw block (`.gitignore` lines, JSON, a diff), a commit hash or a version id unless they ask; offer them instead.
- **Never tell the student a skill or a procedure requires something.** Don't end a question with lines like "The update skill requires a separate yes", don't quote this file, and don't name its steps. Say in plain words what the student is choosing and why it's safe.
- **Read Git without `git diff`, `git log` or `git show`.** The team's settings ask the student before each of those, so each one is an extra box. Use `git status --porcelain`, `git rev-parse`, `git rev-list`, `git ls-tree`, `git cat-file -p`, `git ls-files` and `git merge-base`, and read files on disk with the app's own file reading. This holds in the steps of `aibl-enroll` and `aibl-checkpoint` that this update follows: in place of their `git diff --cached -- <file>`, read `git cat-file -p :<file>` beside `git cat-file -p HEAD:<file>`; in place of `git diff --no-index` between two files, read both and compare them yourself, ignoring line endings.
- Program merges use only verified `<remote>/student`; `template/main` is used only for the approved core-file refresh.
- Never merge over a dirty tree (step 1's private records and course bookmarks aside), overwrite ignored files, resolve a surprise conflict, or apply a changed preview without a new decision.
- Never push except through the student's separately requested checkpoint to their private `origin`.
- In Codex, every write in "In Codex: one permission for each protected write" is its own command, never joined with `&&`, `;` or `|`, with the app's permission asked together with it and one plain line before it. If it isn't allowed, say its waiting line and wait: never another route, never a terminal step for the student, never a claim that it happened.
- Nothing here installs software, grants access, changes global settings, or sends work. The only writes outside the workbench are the real copies of the course's own agents and bridge skills in the user's `.claude` folder, with their record, lock and backup folder (step 6.5), the one file `~/.aibl/workbench.json` (step 7), and the course Langfuse recorder's own hook files, hook entries and library where tracing is already set up (step 7's recorder refresh), each written only on the student's yes. The student's own agents and skills, in Claude Code or Codex, are never moved, replaced or deleted.
